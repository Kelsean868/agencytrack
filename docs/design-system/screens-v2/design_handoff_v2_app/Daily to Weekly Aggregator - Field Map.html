Core rule

The weekly draft is a pure function of the week's daily entries — recomputed, never incremented. weeklyDraft = aggregate(all dailyActivity docs in ISO week). Any create / edit / back-fill of a day re-runs the whole aggregation, so the result is idempotent and edits can't drift. Aggregation sums every logged day regardless of schedule; working-days only affects pace, points-target, and streaks — never the totals.

Points & pace — the anchored numbers

i

The floor is real; the mapping is the work. The weekly activity-point floor comes from the manager standard already in the repo (manager-v2-drill — e.g. L1: dials 40 · tel 10 · F2F 5 · FFI 3 · CI 2 · app 1, scaled by level). Run those floor counts through the existing points engine to get weeklyPointsFloor, then ÷ working days for the daily target. Don't introduce a second set of weights — the daily tally and the floor must use the same engine or the "ahead/behind" call is wrong.

Working days — affects pace, not totals
ConcernBehavior
AggregationAlways sums every logged day in the ISO week (5, 6, or 7). Schedule is irrelevant to totals.
Pace & points targetDenominator = workingDaysPerWeek (profile setting: 5 / 6 / 7). Drives daily target and week-to-date expectation.
StreakA scheduled day off does not break a streak and is not counted as "missed." Logging on an off-day still counts.
Nudges"You haven't logged today" fires only on scheduled working days.
Back-fill & edit semantics
Edit a logged day
Open dailyActivity/{date}, change values, save → triggers aggregateWeek. Full recompute, so the weekly draft always matches the sum of days. No incremental math.
Back-fill a missing day
Creating a past day's doc is identical to editing — same recompute. The week strip's missing-day cue just surfaces the gap; nothing special server-side.
Locked week
Only weeks with status: draft aggregate. Once the weekly is submitted / committed, day docs are read-only; editing requires an explicit reopen. Decision 4.
Zero / empty day
A saved all-zero day is still a logged day (counts for streak + "days logged"), contributing 0 to totals. Distinct from a missing day (no doc).
Logging-mode transitions
TransitionBehavior
daily → weeklyDays already logged this week stay aggregated into the draft; the agent finishes in the weekly wizard. No data loss.
weekly → daily (mid-week)Per the repo's loggingModeService note: a weekly draft converts to a dated catch-up daily entry so the day-level store stays consistent. Decision 5 — confirm the conversion target.
hybridDaily logging + weekly review; aggregation identical. The weekly is always the read-model of the days.

1
Points: recompute vs sum-of-days
Score the aggregated weekly totals once through the engine, or sum each day's point value? Lean: recompute from totals — no rounding drift, single source.
2
Social breakdown storage
Does the weekly store posts / content / engagements separately, or only a single social count? Map the daily sub-fields accordingly — fold or keep distinct.
3
Weekly home for appointments / FFI-scheduled
Confirm which weekly step appts and ffiSched land in (activity vs sales) so the rollup writes the right field.
4
Lock boundary
Exact status that freezes day-level aggregation (draft → submitted), and whether a reopen is allowed after submit.
5
Daily notes → weekly reflection
Concatenate the week's daily notes as a starter for the weekly reflection prose, or leave it blank? Same question for the weekly→daily catch-up conversion target.
