1 · How this app relates to the design system

Read this first — the target is the repo's own tokens, not the _ds bundle

The production app ships its own Nexus design system in src/index.css (Tailwind tokens + @layer components) that is a 1:1 match for the mockups. "Implement the new design system" = port each mockup's look into its existing React component using these repo tokens — never introduce a new hex, and never import the _ds bundle into the app. The _ds bundle + the mockups in this project are design authoring tools; the repo tokens are what ship.

2 · Global rules — apply to every screen

  • Tokens only — every color/space from a token; no new hex. Tailwind @layer utilities (.card / .btn-primary / .input / .shell) before bespoke classes.
  • Both themes — every screen verified in light + dark via tokens (except Kiosk/Meeting = always presentation-dark).
  • Four states — loading (skeleton) / empty (actionable) / error (inline retry) / ready on every data surface. The repo treats these as required.
  • Data via services — src/services/* with tenantId; never query Firestore from components.
  • Type & number — Cabinet Grotesk display, Satoshi body, JetBrains Mono for eyebrows/currency/policy#. Currency via formatCurrency → TTD 24.5K. Tabular, right-aligned nums in tables.
  • Density & glass — dense tables scroll in-card with sticky header + first column; one GlassCard max per screen (top summary); gold only for recognition.
  • a11y (WCAG 2.2 AA) — CI gate green (@axe-core/playwright, eslint-plugin-jsx-a11y): labelled controls, focus-visible rings, ≥44px targets, reduced-motion guards, semantic lists/tables.
  • Motion — .15–.18s ease; reveal-on-scroll one-shot; visible end-state is the base style; no infinite loops on content.
  • No emoji. Only ★ (live/recognition) and ✓ (checks) as text glyphs.

Coverage summary

~30 screens are Shipped on v2 (diff-vs-mockup only) · a handful are Verify / port (Dashboard content deltas, Goals, Login states, emails) · 3 are genuine builds: Planner (agent), Team Planner (manager), CRO / back-office. There is no from-scratch DS migration left — the design system is already in the repo.

4 · The three real builds — where the effort goes

CRO
Delivery Register + 30-day clawback clock; role not routed. Full spec: AgencyTrack — CRO Build Handoff.html. Human-merge gates: cro claim (functions) + branch-scoped deliveries rules.
Planner (agent)
Digitizes the paper Weekly Planner; owns the shared appointments/prospects data. Un-gate the coming-soon planner tab. Spec: Planner & Scheduler Build Handoff.html + planner-scheduler-handoff/.
Team Planner (mgr)
Coaching tier over the agent planner; four trust constraints enforced at the rules layer. Reuses agent components with a stream prop. Spec: same handoff + planner-manager-handoff/.

5 · Per-screen definition of done (checklist)

  • Renders in Shell; correct nav group + tab.
  • Light + dark verified via tokens.
  • No new hex — every value a token.
  • Loading / empty / error / ready all present.
  • Data through a services/* fn with tenantId.
  • Currency via formatCurrency (TTD).
  • Dense tables: scroll-in-card, sticky header/col, tabular nums.
  • One GlassCard max; gold = recognition only.
  • a11y CI green; 44px targets; focus rings.
  • Reduced-motion guarded; no infinite content loops.
  • Matches the mockup; committed per-screen (small PR).
  • Rules/functions changes → human-merge + deploy.

How to work this reference

For each Shipped / Verify row: open the mockup beside the repo component and apply visual deltas only — no rebuild. For the three Build rows: use the dedicated handoff + the unified Claude Code kickoff. Work one screen per branch, small PRs, verifying the definition-of-done each time.
