# F2.2 — Email-to-BM on Joint-Call Submit: Design Questions

Recon doc for [FOLLOW_UPS.md § F2.2]. Audited 2026-05-28.

---

## 1. Current surface (what's built)

### F2.1 (shipped)
On `addJointCall()`, `jointCallsService.js:108–118` calls `resolveBmInfo(tenantId, agentId)` → creates an in-app notification for the BM (if BM exists and is not the author). The in-app signal is live.

### `mail/` queue pattern (established in PR #229)
Cloud Functions write to the top-level `mail/` collection via Admin SDK. The Firebase Trigger Email Extension picks up each doc and dispatches via SendGrid. Existing templates in `functions/email-templates/`:

| Template pair | Purpose |
|---|---|
| `password-reset.{txt,html}` | Invite / password reset (new-user flow) |
| `monday-nudge.{txt,html}` | Monday reminder to complete weekly report |
| `sunday-nudge.{txt,html}` | Sunday deadline reminder |

Template variables use `{{handlebars}}` syntax. Helper: `buildMailDoc(to, subject, txtFile, htmlFile, vars)` in `functions/utils/email.js`.

### Joint-call Firestore schema (collection: `tenants/{tid}/users/{agentId}/jointCalls/{callId}`)

Fields written by `addJointCall()`:
- `agentId`, `agentUnitId`, `tenantId`
- `authorUid`, `authorName`, `authorRole`, `authorRoleRank`
- `appointmentDate` (string), `appointmentTime` (string)
- `appointmentKept` (bool)
- `nextMeetingDate` (string, populated if `appointmentKept = false`)
- `meetingType` — enum: `demonstration` / `observation` / `collaboration`
- `needCovered` — enum: 9 values (income_protection, mortgage_or_debt, education_funding, retirement_planning, final_expenses, wealth_accumulation, critical_illness_or_health, business_protection, other)
- `comments` (string ≤ 2000)
- `saleMade` (bool)
- `coachingMinutes` (float)
- `trainingIdentified` (string ≤ 1000)
- `prospectInfoId` (string ≤ 128)
- `createdAt`, `updatedAt` (serverTimestamp)

### `resolveBmInfo(tenantId, agentId)` — client-side
`jointCallsService.js:48–56`: `agentId` → user doc `.branchId` → `branches/{branchId}.managerId` → `bmUid`. Returns `{ bmUid, agentName }`. Used by F2.1 for in-app notification. The CF for F2.2 will need a server-side equivalent (same logic, Admin SDK reads).

BM email address: must come from `admin.auth().getUser(bmUid).email` (Auth record), not from the Firestore user doc (no `email` field guaranteed).

## 2. F2.2 scope

New deliverables:
1. **Cloud Function** — listens for joint-call creation and writes a `mail/` doc addressed to the BM
2. **Email template pair** — `joint-call-notify.txt` + `joint-call-notify.html` in `functions/email-templates/`
3. **No UI changes** — this is fully server-side

F2.2 does NOT include:
- Changes to `addJointCall()` or the joint-call form
- Any new Firestore collections or rules
- Any changes to the F2.1 in-app notification path

## 3. Design questions

---

### Q1 — CF trigger mechanism
**How does the CF know a joint call was submitted?**

| Option | Mechanism | Tradeoff |
|---|---|---|
| **A. Firestore `onCreate` trigger** | `functions.firestore.document('tenants/{tid}/users/{agentId}/jointCalls/{callId}').onCreate(...)` | Automatic — fires on every create, no client coordination. `onCreate` (not `onWrite`) guarantees only new docs, not updates. |
| **B. Explicit callable CF** | Client calls `functions.httpsCallable('notifyBmJointCall')` after `addJointCall` succeeds | Mirrors `resendInviteEmail` pattern. Client controls timing but can forget to call or be interrupted. |

**CC recommendation: Option A (`onCreate` trigger).** It fires reliably on every new joint call regardless of client path, and `onCreate` avoids double-fires on updates. The downside — the CF can't return confirmation to the UI — is acceptable since email is a background concern (same as existing cron-based nudge emails).

**Question for Kyron:** Is Option A (automatic trigger) the right call, or do you prefer the explicit callable pattern (B) for consistency with `resendInviteEmail`?

---

### Q2 — What fields appear in the email body?
**The email should communicate enough for the BM to know who was observed and the key outcomes.**

Proposed field set for the email template (minimal + outcomes):

| Field | Included |
|---|---|
| Author name + role | ✅ |
| Agent name | ✅ |
| Appointment date | ✅ |
| Meeting type (Demonstration / Observation / Collaboration) | ✅ |
| Need covered | ✅ |
| Sale made (Y/N, prominent if Y) | ✅ |
| Coaching minutes | ✅ |
| Training identified | ✅ (if non-empty) |
| Comments | ❓ (see Q3) |
| Appointment kept / next meeting date | ✅ if kept=false |

**Question for Kyron:** Should the full `comments` field appear in the email, or only if the SM/BM specifically wants it? Comments can be up to 2000 chars — that's long for an email. Options: (a) always include, (b) include only first 300 chars with "See full notes in app" CTA, (c) exclude entirely.

---

### Q3 — Email subject line: should `saleMade = true` change it?
**The most actionable outcome of a joint call is a sale. Should the subject line reflect this?**

Options:
- A. Static subject: `Joint call logged for {agentName}` (always)
- B. Dynamic subject: `Joint call — SALE MADE: {agentName}` vs `Joint call logged: {agentName}` (branch on `saleMade`)

Option B makes BM email triage faster (sale vs. coaching vs. observation). No implementation cost difference — same template, one `{{#if saleMade}}...{{/if}}` conditional.

**CC recommendation: Option B.** The BM benefits from a scannable inbox subject.

**Question for Kyron:** Dynamic subject (B) or static (A)?

---

### Q4 — Should the email include a deep-link CTA?
**"View in app" links are possible (straight to the agent's Joint Calls panel) but require the app URL + agent path.**

Options:
- A. No CTA link (email is purely informational)
- B. Generic link to the manager dashboard (no specific deep-link routing): `https://agencytrack.vercel.app`
- C. Agent-specific link: `https://agencytrack.vercel.app` (Vercel has no path-based deep-links for Firebase Auth flows — agent-specific routing depends on auth state)

**CC recommendation: Option B.** A bare app URL is safe (no token in the URL) and useful. A true deep-link would require the BM to already be signed in, which is not guaranteed. Revisit if in-app URL routing matures.

**Question for Kyron:** Include app link (B), no link (A), or something else?

---

### Q5 — BM-is-author skip rule
**F2.1 already skips the in-app notification when `bmUid === authorUid` (BM logs the call themselves — they don't need a notification about their own action). Should the email follow the same rule?**

CC recommendation: **Yes, mirror the F2.1 skip rule.** If the BM authored the joint call, they clearly know about it — emailing them would be noise.

**Question for Kyron:** Confirm this skip rule, or should the BM always receive an email regardless of authorship?

---

### Q6 — Should the SM also receive this email?
**The Sales Manager has company-wide visibility. Do they need to be cc'd on every joint-call email to the BM?**

Options:
- A. BM only (F2.2 scope — keep it minimal)
- B. BM + SM (resolve SM via the branch's SM assignment; if no SM, BM only)
- C. Configurable per-tenant (tenant_admin can toggle SM cc in settings)

The SM notification use-case is more for executive oversight of coaching activity, which is already surfaced in the SM summary view (if built). A blanket CC on every individual joint call email would be high-volume noise for the SM.

**CC recommendation: Option A (BM only).** If SM visibility is needed, the in-app SM activity summary (Track I) is a better vehicle than email CC.

**Question for Kyron:** BM only (A), or cc the SM (B)?

---

### Q7 — Non-fatal failure handling
**If BM email resolution fails (no `branchId` on agent, branch doc missing, BM has no Auth email), what should happen?**

Consistent with `resendInviteEmail` pattern: email failure should be non-fatal and NOT block the joint-call save (which happens client-side before the CF fires). The CF should:
1. Attempt BM resolution → if `bmUid` null: log and return (no email)
2. Attempt `admin.auth().getUser(bmUid)` → if email empty: log and return
3. Attempt `mail/` doc write → if fails: `console.warn` + continue (same as `resendInviteEmail:543-547`)
4. No retry mechanism (Trigger Email Extension handles delivery retries)

**This is not a question — it follows the established pattern.** Confirmed OK unless Kyron disagrees.

---

### Q8 — Audit collection
**`resendInviteEmail` writes an audit doc to `auditInviteResends` for every send attempt. Should F2.2 have an equivalent?**

`auditInviteResends` tracks actorUid, targetUid, IP, userAgent, emailQueued. This made sense for an explicitly user-triggered action (resend) where actor accountability matters.

For F2.2, the CF is triggered automatically by a Firestore write — there's no actor in the traditional sense. The joint-call doc itself (`createdAt`, `authorUid`) is the audit trail.

**CC recommendation: No audit collection for F2.2.** The joint-call doc already records who submitted and when. If email delivery confirmation is needed, the Trigger Email Extension updates the `mail/` doc status field — that can be queried if needed.

**Question for Kyron:** Agree with no audit collection, or do you want a lightweight audit trail (callId + bmUid + emailQueued per send)?

## 4. Proposed implementation shape (after design questions resolved)

```
functions/
  index.js                          ← new onDocument.onCreate export: notifyBmJointCallEmail
  email-templates/
    joint-call-notify.txt           ← new
    joint-call-notify.html          ← new
```

CF sketch (Option A trigger):
```javascript
exports.notifyBmJointCallEmail = functions.firestore
  .document('tenants/{tenantId}/users/{agentId}/jointCalls/{callId}')
  .onCreate(async (snap, ctx) => {
    const { tenantId, agentId } = ctx.params;
    const call = snap.data();

    // 1. Resolve BM uid + email
    // 2. Skip if bmUid === call.authorUid
    // 3. Look up BM Auth email via admin.auth().getUser(bmUid)
    // 4. Write mail/ doc via buildMailDoc('joint-call-notify.txt/html', vars)
    // All failures non-fatal (try/catch with console.warn)
  });
```

Template variables needed: `authorName`, `authorRole`, `agentName`, `appointmentDate`, `meetingType`, `needCovered`, `saleMade`, `coachingMinutes`, `trainingIdentified` (conditional), `appointmentKept`, `nextMeetingDate` (conditional), `comments` (conditional on Q2 answer), `appUrl`.
